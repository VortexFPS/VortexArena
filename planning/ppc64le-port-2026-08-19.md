# Building Vortex Arena on IBM POWER (ppc64le) — decision and state

**Status: DECIDED and PARTLY BUILT (2026-08-19).** The target is **ppc64le** — 64-bit little-endian
PowerPC, POWER8 and newer. **No binaries are published for it and none are planned:** it is supported as
a build-from-source platform, client and dedicated server alike. The tooling, the export presets and the
one required engine patch are in this repo now; the two steps that need actual POWER hardware are
written out below and have not been run, because nobody has run them.

This document exists so the next person does not have to re-derive which of the four plausible walls are
real. Three of them are not.

---

## The decision

| | |
|---|---|
| **Target** | `ppc64le` — little-endian, POWER8+ (Talos II / Blackbird workstations, POWER9/10 servers) |
| **Not a target** | big-endian `ppc64`. See "Why not big-endian" below — it is refused by name, not left to fail late |
| **First goal** | the **dedicated server**: headless, no GPU driver question, and the thing POWER hardware realistically runs |
| **Second goal** | the graphical client, which adds a Vulkan/driver question and nothing else new |
| **Engine** | built from source on the machine. Upstream publishes no POWER binary and never has |
| **.NET** | Red Hat / IBM builds for `linux-ppc64le`. Not Microsoft's package feed, which is x64-only |

### Why not big-endian

Two independent blockers, either of which is sufficient:

1. **Godot 4 is little-endian only.** Its SConstruct aliases `ppc64le` **to** `ppc64`, i.e. the engine's
   `ppc64` already means the little-endian one.
2. **.NET publishes no big-endian PowerPC runtime at all.** Every .NET-on-POWER announcement from IBM,
   Microsoft and Red Hat names `ppc64le` and only `ppc64le`. So even a successfully compiled engine
   could not load a single one of this game's C# assemblies.

Only after those does the game's own code matter, and it would: ten call sites use `BitConverter`, which
follows host byte order (listed in `src/VortexArena.Formats/BinaryUtil.cs`, whose header carries the full
statement of the tree's endianness posture). They are correct on every target the engine can run on.

`tools/build-engine.sh` refuses a big-endian host by name, up front, rather than letting it discover this
three hours into a compile.

## What was checked, and what turned out not to be a problem

Everything in this section was verified against the pinned engine version (Godot 4.6.3-stable) and this
tree, on 2026-08-19 — not against Godot or .NET in general.

### The game's own C# is architecture-clean

Nothing here needed changing, which is the single biggest reason this port is tractable:

- **No x86 intrinsics.** Zero occurrences of `System.Runtime.Intrinsics` across `src/`, `game/`,
  `tests/`, `tools/`.
- **No `MemoryMarshal` / `Unsafe.As` struct reinterpretation.** Zero occurrences.
- **No native third-party dependencies.** The entire solution's NuGet references are Roslyn (an analyzer,
  `netstandard2.0`), xunit and `Microsoft.NET.Test.Sdk` — all managed and architecture-neutral. Nothing
  like ONNX Runtime or a native physics library, which would have no POWER build and no way to get one.
- **Three P/Invokes, all Windows-only and already guarded** — `user32!GetForegroundWindow` behind
  `OperatingSystem.IsWindows()` in `game/MouseCapture.cs`, and two `kernel32` lookups in
  `game/client/RenderDocCapture.cs` that no-op unless the process was launched under RenderDoc.
- **The binary format parsers already declare their endianness** rather than inheriting the host's —
  `BinaryUtil.cs` reads little-endian explicitly, `Dpm/DpmBinary.cs` big-endian explicitly.

### The engine builds for it

- `platform_methods.py` lists `ppc64` in `architectures`, and `architecture_aliases` maps
  `ppc64le → ppc64`.
- `platform/linuxbsd/detect.py` lists `ppc64` in `supported_arches`, and its `get_flags()` includes
  `"mono"` in `supported` — so `module_mono_enabled=yes` is a legal combination, the mono module's gate
  being platform-level rather than architecture-level (`modules/mono/config.py`).
- **AccessKit needs no special flag**, contrary to the first read of `detect.py`. Its per-architecture
  `LIBPATH` table (arm64, arm32, rv64, x86_64, x86_32 — no ppc64) is consulted **only when
  `accesskit_sdk_path` is non-empty**. It is empty by default and empty in CI, which takes the `else`
  branch to `ACCESSKIT_DYNAMIC` and needs no SDK. Passing `accesskit=no` would be a silent configuration
  drift from the CI-built templates for no gain.

### One degradation, and it is small

`modules/raycast` — the Embree-backed module behind lightmap baking and occlusion-culling baking — allows
only `x86_64`, `arm64` and `wasm32` in its `can_build`, so it disables itself on POWER. An editor built
there cannot bake lightmaps or occlusion. This is an authoring feature, not a runtime one, and it does not
touch a dedicated server at all.

## The one real blocker, and the patch that removes it

Godot's C# export plugin turns the engine's architecture name into a .NET runtime identifier through a
hardcoded switch in `modules/mono/editor/GodotTools/GodotTools/Export/ExportPlugin.cs`:

```csharp
"x86" => "x86", "x86_32" => "x86", "x64" => "x64", "x86_64" => "x64",
"armeabi-v7a" => "arm", "arm64-v8a" => "arm64", "arm32" => "arm", "arm64" => "arm64",
_ => throw new ArgumentOutOfRangeException(nameof(arch), arch, "Unexpected architecture")
```

There is no PowerPC arm, so `--export-release` for a ppc64 preset throws before writing anything — the
whole platform is unreachable from the exporter however well the engine compiles.

**The C++ half of the same exporter already knows the architecture.**
`platform/linuxbsd/export/export_plugin.cpp` maps ELF `e_machine` `0x0015` (EM_PPC64) to `"ppc64"` and
offers `ppc64` in the `binary_format/architecture` enum. Only the C# half is missing, so the fix is one
arm: `tools/engine-patches/godot-4.6.3-ppc64-dotnet-rid.patch`, pinned by sha256 in
`tools/engine-patches/engine.lock.json`, verified to apply cleanly to `4.6.3-stable`. It is a genuine
upstream candidate.

Note the asymmetry, which is not a typo: Godot's architecture is `ppc64`, .NET's RID is `ppc64le`.

### Running from source does not go through any of that

`modules/mono/mono_gd/gd_mono.cpp` resolves `libhostfxr` from the **system** .NET installation in editor
mode, and only an **exported** game probes for a bundled runtime beside its binary. So `vx build`,
`vx test` and `vx run debug` need a working editor and a system .NET — no RID mapping, no export plugin,
no patch. Only shipping a build needs the patch.

## .NET on this architecture

.NET 7 and 8 run on `linux-ppc64le`, delivered by Red Hat and IBM as distro packages —
`dnf install dotnet-sdk-8.0` on RHEL 8.9 / 9.3. Microsoft's own Linux package feed is x64-only.

Two consequences that bite in specific places, both confirmed against nuget.org on 2026-08-19:

- `Microsoft.NETCore.App.Runtime.linux-ppc64le` **404s** on the flat-container index, while
  `Microsoft.NETCore.App.Runtime.linux-x64` returns a full version list. The package ID form is right;
  the package is genuinely not published. A self-contained publish for this RID has to source its runtime
  pack from the machine's own .NET installation (Red Hat installs packs under `/usr/lib64/dotnet/packs/`)
  rather than from a restore.
- `Microsoft.NETCore.App.Crossgen2.linux-ppc64le` **404s** likewise, which is why `PublishReadyToRun` is
  turned off for this RID in `VortexArena.csproj`. Left on, the export fails at restore with `NU1101`,
  naming a package and not a cause.

## What has not been done, because it needs the hardware

Neither step below has been run. They are written out in full so that running them is mechanical.

### S1 — Prove the managed half

On the POWER box, with .NET 8 for ppc64le installed:

```bash
./vx doctor            # reports: host ppc64le, no upstream engine build
./vx build             # the class libraries and the Godot host's C#
./vx test              # 4233 with maps installed, 4060 without - the map-dependent theories
                       # generate no cases rather than failing. 0 failures either way.
ci/ci.sh --no-smoke    # the gate, minus the parts that need an engine
```

Nothing here needs Godot. A green run proves the game logic is architecture-clean in fact rather than by
inspection, and everything after it is toolchain work.

### S2 — Build the engine

```bash
./vx build-engine --dry-run                 # read the plan first; it prints every command
./vx build-engine --target editor --install # editor only: enough for the whole development loop
./vx build-engine --install                 # editor + release template: needed to ship
```

Hours, not minutes, and it needs a C++ toolchain, `scons` and the .NET SDK. `--target editor` is the
smaller commitment and unlocks `vx run debug`, `vx server`, and `ci/ci.sh`'s headless smoke.

### S3 — The export presets — DONE (2026-08-19)

**Policy, decided the same day: this project publishes no ppc64le binaries and does not intend to.**
ppc64le is supported as a *build-from-source* platform — the game is meant to compile and run there, not
to arrive as a download. Both presets exist so that a person on POWER can produce a real release build of
the **client and the dedicated server** locally, which is the whole point; neither is in the release
matrix.

`export_presets.cfg` now carries `linux-client-ppc64le` (preset.5) and `linux-dedicated-ppc64le`
(preset.6), both pointing at `tools/engine-templates/godot.linuxbsd.template_release.ppc64.mono` — the
file `./vx build-engine --arch ppc64 --install` writes.

Three things keep that from leaking into a release, none of them relying on anyone remembering:

- `.github/workflows/release.yml` names its presets explicitly and does not name these.
- `vx export --all` means the *shipping* matrix (`Wrappers.Presets`); the source-only pair lives in
  `Wrappers.LocalBuildPresets` and is reachable by name, or automatically via `DefaultPreset()` when the
  host really is ppc64le.
- `tools/make-manifest.py` has no download key for them at all — see S4.

They needed a **third category** in `engine.lock.json`: `local_build_presets`. The existing two could not
describe this and the audit would have rejected either. A *pinned* preset names a published artifact and
a sha256; a *declared gap* must have an **empty** `custom_template/release`, because that category means
"runs on the stock template" (`check_declared_gap` fails a non-empty field on purpose). A source-only
platform is neither: its field must be **populated** — there is no stock PowerPC template to fall back
to, so an empty field fails loudly instead of silently, inverting the usual danger — and it can never
carry a hash, because Godot does not build reproducibly.

So `check_local_build` asserts the *shape*: the field is populated, it names the declared template, and
**that file exists before an export is attempted**. The last one is what earns its keep — without it
Godot aborts with `Mismatching custom export template executable architecture: found "invalid"`, which
reads like an architecture problem and tempts you to blank the field, the one genuinely dangerous value.
With it you get the command to run:

```
$ python tools/verify-engine-template.py --preset-config linux-client-ppc64le
FAIL: linux-client-ppc64le: the template it names is not on disk yet — tools/engine-templates/…ppc64.mono
    Nothing can export this preset until it exists. Build it with: ./vx build-engine --arch ppc64 --install
```

Note the two spellings once more: the **template filename and `binary_format/architecture` say `ppc64`**
(Godot's name), while the **export path and package name say `ppc64le`** (the public name, which states
the endianness).

### S4 — The launcher's half: build from source, not download

`latest.json` now carries a **`source_build`** block alongside `platforms`, stamped with the release tag:

```json
"source_build": {
  "linux-ppc64le": {
    "reason": "...no upstream Godot build for this architecture...",
    "clone": "https://github.com/VortexFPS/VortexArena.git",
    "ref": "v0.2.0",
    "steps": ["./vx setup --yes", "./vx build-engine --install", "./vx build",
              "./vx export --preset linux-client-ppc64le", "./vx run"],
    "needs": ["a C++ toolchain", "scons", ".NET SDK 8+", "python3", "git"],
    "expect": "hours: the engine is compiled twice..."
  }
}
```

**Why a declaration rather than an omission.** Absence is ambiguous: a missing platform key looks
identical to a release whose Linux job failed, so a launcher cannot tell "we do not build this" from
"today's build is broken". Saying it out loud lets VortexLauncher do the right thing on POWER — build
from source at the same ref the release names — without hardcoding an architecture list that would then
drift from this repo. `ref` is the piece it cannot derive for itself, and it is what makes a source build
track releases rather than whatever `main` happens to be.

**The other half is not started.** `latest.json` is the only interface between the two repos, so this is
a two-repo change; this side can ship first because a launcher that has never heard of `source_build`
ignores the key and behaves exactly as it does today.

## Things a reader should not have to rediscover

- **`ppc64` and `ppc64le` are the same target under two names.** Godot's build system and export presets
  say `ppc64`; uname, .NET's RID, every distro and this tree's public-facing names say `ppc64le`.
  `Env.HostArch` returns the public one and `Env.GodotArch` converts.
- **Building the editor is not optional even when you only want a template.** The C# glue is generated by
  running an editor binary, so a `.NET` template always costs two engine compiles.
- **A dedicated server is the cheap target.** No GPU, no Vulkan driver question, no shader cache, and it
  is what POWER hardware is actually deployed for.
- **The client's GPU story is a driver question, not a port question.** An AMD card on Mesa's RADV is the
  realistic path on a Talos II; nothing in this game or in Godot cares which CPU is issuing the Vulkan
  calls.
