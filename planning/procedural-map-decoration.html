1Goals & non-goals

The pitch: take the basic geometry of any existing map (a compiled .bsp or an authored .map) and procedurally decorate it into something like the CONCEPT shot — weathered layered materials, moss and grime placed where physics says they belong, torches that are actually lit, detail geometry where the silhouette deserves it — while keeping every knob hand-editable in the running game.

  • G1 — Multi-layer texture blending in the renderer: several full material layers (albedo/normal/roughness/height) crossfading per-pixel on one surface. This is the core renderer feature the whole doc hangs off; the DarkPlaces/NetRadiant stack effectively does not have it (Appendix A).
  • G2 — Procedural mask generation: dirt, moss, burn/scorch, rain streaks, edge wear, sun bleach — computed from the map's own geometry (occlusion, corners, height on wall, sky exposure), with per-zone and per-surface-class parameter overrides (top of wall vs. bottom, corners vs. flats), and smooth continuation across adjacent surfaces.
  • G3 — Procedural detail geometry: rule-driven prop placement (torches, trims, debris, banners), decal projection, floor relief.
  • G4 — Decoration-geometry amplification: detect lattice/ornament brushwork (the spike crowns in the screenshots) and regenerate it at higher fidelity.
  • G5 — In-game, real-time editing: an editor game mode with two player states (free-fly EDIT / instant PLAYTEST), first-person geometry manipulation — grabbable verts/edges/faces, move & rotation handles, grid + geometry snapping with HUD readouts (§11.3–11.4) — orthographic top/front/side views with exact wireframe lines and axis-locked editing, quick render-mode toggles (§11.5), plus decoration editing with manual painting layered non-destructively on the procedural output. Server may bake heavy passes (lighting, mask bakes) and stream results to clients.
  • G6 — A native map format where the editable representation is the shipping representation, with a regenerable bake cache for runtime efficiency (the ".map vs .bsp" split collapsed into one package).
  • G7 — World dressing beyond the brushwork (v1.2): generated skyboxes with selectable art styles (painted daylight, golden hour, overcast, deep space) and a dynamic weather system with falling rain (§10.2–10.3) — plus, at lower priority, generated terrain / outside-the-map vista geometry (§8.5) and paintable foliage with style variation that reacts to wind and explosions (§8.6).
  • G8 — Live lighting & the gameplay layer (v1.3): lighting previewable in real time while editing, with baking made progressive rather than batch (§10.1) — and, lower priority, deterministic balance-driven item placement, player-count-aware map selection, demo-mined heatmaps (§12), and auto-detected spawn-point presence pads (§8.7).

Non-goals (for this doc): a full Radiant replacement — first-person tools (§11.4) plus single-pane ortho views (§11.5) cover geometry editing, and the clipper (plane split) makes the cut, but boolean CSG ops (subtract / hollow) and a docked quad-view desktop UI stay out until the loop is proven; replacing q3map2 for classic-map compatibility; PBR-ifying the DP-faithful renderer for existing stock maps (decorated maps are a deliberate fork-forward feature; the Q3-stage material path stays intact for parity).

v1 priority — editor first Build order: the .vmap format (§11.2) → the .bsp/.map importers (§11.1) → the editor game mode with first-person tools, ortho views & render modes (§11.3–11.6) come first; procedural decoration (§4–§10) follows once the format + editor loop exists. The decoration sections remain in this doc as the target the format must not design itself away from — and decoration's editing UX gets cheaper for the reordering, since it lands on the editor's op/undo/HUD/replication rails instead of bespoke transient plumbing. Resequenced roadmap in §13.
Design stance Everything is rules → fields → masks → layers, with manual edits stored as deltas at each stage rather than baked-over results. Re-running the procedural pass never destroys hand work; hand work never blocks re-tuning the rules. This one invariant drives the format (§11), the editor, and the networking.

Two observations worth pinning. 3.2Where the DarkPlaces/NetRadiant stack stops

The classic stack's only per-pixel-variation mechanism is per-vertex alpha: q3map2 seeds vertex alpha via q3map_alphaMod volume brushes (or dotProduct2-style terrain shaders), and a two-stage shader crossfades layer B over layer A with alphaGen vertex / alphaFunc. That gives you the famous Q3 terrain blends — and nothing more:

  • Resolution = tessellation. The blend can only change where vertices exist. On a big flat wall brush there are 4 vertices; no gradient detail without manually chopping geometry.
  • Practically 2 layers. Every extra layer is another full multiply/blend render pass over the surface.
  • Diffuse-only. No normal/roughness/height participation, so blends look painted-on, not material-vs-material.
  • No authoring UI. NetRadiant has no vertex painting; artists sculpt invisible alphaMod brushes and recompile to see results. Nothing is editable at runtime, ever — the pipeline is author → q3map2 → restart.
  • No procedural placement. Nothing computes occlusion/curvature/exposure; every weathering decision is a hand-placed decal or a bespoke texture variant (wall_mossy_bottom_02.tga multiplication — the reason idTech-era texture sets balloon).

So G1 is not "catch up to modern engines" as a nicety — it removes the single bottleneck that forced the entire texture-variant workflow the original assets are built around. Full comparison table in Appendix A.

4The map anatomizer — feature fields everything else consumes

One analysis pass runs over the base geometry and produces feature fields — scalar/vector data per surface point that answer "what is this spot?" Every downstream system (weathering generators §6, prop rules §8, amplification §9) reads these fields instead of doing its own geometry queries. This is the piece that makes rules composable and the piece with the most reuse, so it's worth building well.

Key property — world-space evaluation, chart-space storage All fields are evaluated in world space (traces, distances, flows don't care about face boundaries) and then sampled into per-face chart texels (§5.1). Because two faces meeting at an edge sample the same world-space field, masks agree across the seam by construction — the "blending/smoothing around adjacent surfaces" requirement falls out for free, with only a small seam-dilation pass needed to hide chart-boundary filtering.

Cost & caching: the anatomizer is a bake, not a per-frame system. For editing it must be incremental — fields are stored in tiles keyed by a hash of (geometry region, parameters), and a geometry edit dirties only intersecting tiles. Budget target: full first bake on a stock map in tens of seconds on the server; incremental re-bakes sub-second for a local edit. (Per house rules, any runtime portion gets a Prof.Sample scope.)

5Multi-layer texture blending — the renderer feature

The contract: a decorated surface renders base material + up to N weather/variation layers, each a full material (albedo, normal, roughness, height), blended per-pixel by mask values, with height-aware blend edges (moss grows between cobbles before it covers them — the single biggest "looks real vs. looks painted" factor).

5.1Where masks live — three options

OptionHowVerdict
altPer-vertex channels Masks in COLOR/CUSTOM vertex attrs; optionally subdivide faces for resolution. The Q3 approach with the Q3 problem: resolution tied to tessellation. Fine as a fallback tier for low graphics settings; not the primary store.
recommendedChart-space mask atlas ("weather atlas") Reuse the existing lightmap UV2 charts (MapLoader already builds the atlas + gutters) at a higher, per-face-scalable density (e.g. 4–16× lightmap texel density, denser where masks have detail). Masks are RGBA tiles in one atlas texture; the same charts later host our own baked lighting (§10). Unique texels on every surface, resolution decoupled from geometry, trivially paintable, streams in tiles. The unwrap problem — normally the hard part — is already solved for lit faces; unlit/vertex-lit faces need a chart allocation pass (simple planar projection per face is enough; these are brush faces, not organic meshes).
alt / laterWorld-space sparse 3D masks Clipmap or sparse-brick 3D texture sampled by world position — no UVs at all, perfectly seamless. Elegant (seams impossible, volumetric effects like "burned region" trivial) but memory-hungry and overkill for v1. Worth keeping as the possible v2 store; the shader interface below doesn't preclude it.

Layer count per texel: RGBA8 gives 4 weather channels; a second atlas page doubles it. If maps want many layers, switch to indexed splatting (per-texel: 2–3 layer indices + weights, UE-landscape style) — but start with fixed channels; the weathering set (moss/dirt/soot/wear + wet in a second page) fits.

5.2The layered shader

Extend the existing generated-shader pipeline (Q3StageGlsl) with a "layered" material mode. Weather layer textures live in Texture2DArrays (one array each for albedo/normal/rough-height packs) shared by every decorated material — one texture bind set for the whole map, layer choice is an index.

// sketch — decorated-surface fragment stage
uniform sampler2DArray wx_albedo : source_color, filter_linear_mipmap;
uniform sampler2DArray wx_nrh;            // normal.xy, roughness, height packed
uniform sampler2D      wx_mask;           // weather atlas tile (chart space, UV2-family)
uniform float          wx_layer[4];       // which array layers this material's channels map to
uniform float          wx_scale[4];       // world-space tiling per layer

vec4 m = texture(wx_mask, uv_chart);                       // moss, dirt, soot, wear
vec3 base = /* existing Q3-stage or PBR base result */;
float base_h = /* base layer height, from its own pack */;

for (int i = 0; i < 4; i++) {
    vec3 wa = triplanar(wx_albedo, wpos * wx_scale[i], wx_layer[i], wnormal);
    vec4 nrh = triplanar(wx_nrh,  wpos * wx_scale[i], wx_layer[i], wnormal);
    // height-aware blend: mask biased by layer-vs-base height contest → crisp organic edges
    float w = height_blend(m[i], nrh.a, base_h, wx_sharp);
    base = mix(base, wa, w);
    // (normal & roughness mixed the same way; wear channel instead *reveals* — subtracts toward substrate)
}
  • Triplanar world projection for weather layers — no UVs to author or align, seamless across faces, correct on slopes. (Base layers keep their existing Q3 UVs.) Cost note: naïve triplanar = 3 samples/layer; use the dominant-axis single-sample variant with a small blend band on edge texels.
  • Channel semantics differ: moss/dirt/soot are cover layers (mix toward the layer); wear is a reveal layer (mix toward a substrate — bare stone under plaster, bright metal under paint — defined per base material); wet modifies roughness/darkens albedo rather than adding a layer.
  • Uniform mechanics: the mask tile and layer-index table vary per surface-chunk material. Remember the instance-uniform trap (vertex-stage instance uniforms are inert → per-material duplicates); mask sampling is fragment-stage so instance uniforms are usable, but per-chunk ShaderMaterial duplicates with a shared shader are the safe default we already use elsewhere.
  • Perf discipline: new generated shader variants must register with GpuWarmPass (pipeline-compile hitches), ship with Prof.Sample scopes, and pass tools/perf-smoke.ps1. Provide a cvar tier: full (height-aware, per-pixel), reduced (no height contest, dominant-axis triplanar), off (masks collapse to the vertex-tier fallback → still roughly right on low-end).

5.3Automatic texturing & alignment for bare geometry

For the "hand it bare geometry" case (a greybox .map, or replacing a surface's material wholesale), the same world-projection machinery assigns base textures without manual alignment:

  • Box/triplanar mapping by surface class — floors and ceilings get XY-planar projection, walls get the dominant wall axis, at a world-units-per-tile scale from the material definition. This is what "auto-align" means in practice: world-anchored UVs are always aligned, by construction, including across brush cuts (where Radiant's per-face offsets constantly drift).
  • Trim detection — narrow faces adjacent to large faces (sills, ledges, doorframes, steps) get the material's trim variant fitted along the face's long axis (classic trim-sheet fitting: pick the trim strip whose height matches the face, stretch along length).
  • Material grammar per zone — a zone's palette ("sandstone set: wall=block, floor=cobble, trim=carved band") lets one click re-dress a whole greybox area; the weathering pass then makes it non-uniform.

6Procedural weathering generators

Each generator is a pure function fields × params → mask-channel contribution, run over chart texels. They compose by writing into the shared mask channels; ordering only matters for reveal-type layers. All parameters are per-rule-instance, overridable per zone and per surface class — that's the "different settings for corners vs. top vs. bottom of walls" requirement, expressed once, uniformly.

GeneratorField recipe (defaults)Notes
Dirt / dust AOk × concave-edge proximity × (1 − sky exposure), floor bias; extra in cobble crevices via the layer height contest. The universal grime everyone reads as "lived-in". Usually the first channel to enable.
Moss / damp low height-above-floor falloff × concavity × sheltered-but-not-dry sky exposure band × material porosity (stone yes, metal no). Damp = same recipe, wider, feeds the wet modifier at low strength. Matches CONCEPT: arch feet, wall bases, shaded corners. Noise-break the edges (world-space FBM) so bands never read as level curves.
Edge wear / chipping convex-edge distance falloff × traffic/hand-height boost (waist-height band on walls near walkways, from the nav field) → reveal channel. With a normal-map contribution at the reveal boundary this sells "geometry damage" with zero geometry.
Rain streaks gravity-flow line integration from drip seeds (undersides of sky-exposed horizontal edges), length/decay params × sky exposure of the seed. The distinctive vertical grime under ledges in CONCEPT. Streak texture advected along the flow field, not just a vertical gradient.
Burn / scorch proximity cone above flame entities (soot rises: bias along −gravity) + author-painted burn volumes for "this wing burned"; darkens albedo, kills roughness variation, optional ember-glow emissive at high intensity. Explicitly dynamic-editable in the brief: painting a burn volume in-game re-runs just this generator in the dirtied tiles — sub-second loop (§11.7).
Sun bleach sky exposure × alignment with the map's sun direction → subtle desaturate/brighten of base albedo. Cheap; makes outdoor tops read distinct from sheltered bottoms, reinforcing the vertical story.
Traffic wear bot-nav edge usage splatted onto floors → polish (roughness down) + dirt removal along path centers, accumulation at edges. Free art direction from data we already have; also subtly telegraphs routes to players.

Determinism: generators are seeded and pure — same inputs, same masks, on any machine. That keeps server-bake vs. client-regen interchangeable (§11.7) and makes bakes content-addressable.

7Manual painting & overrides

Procedural output is the base coat; humans art-direct on top. The non-destructive rule from §1 concretely:

  • Mask painting — in-game brush (radius/strength/falloff/noise) painting directly into mask channels, projected onto surfaces from the camera ray. Strokes are stored as a sparse delta tile set (chart-space tiles containing only painted texels + blend op: add/subtract/set/scale-procedural). Final mask = procedural ⊕ deltas. Re-running the procedural pass (after a rule tweak or geometry edit) replays deltas on top — hand work survives.
  • Parameter overrides — every rule parameter editable at three scopes: global → zone → surface selection. Live sliders re-run affected generators incrementally (this is the fun demo: drag "moss amount" and watch the courtyard green up in real time).
  • Locks & freezes — a surface/zone can freeze its procedural result (turn current masks into a delta baseline) so later rule edits elsewhere can't disturb an approved area.
  • Prop overrides — §8 placements are suggestions until accepted; each instance can be moved/deleted/swapped, recorded as instance-level deltas against the rule's output (rule re-runs keep the overrides by stable placement IDs: rule id + surface id + sequence).

8Detail geometry, props, terrain & foliage

8.1Rule-based placement

Declarative rules over anatomizer fields, evaluated to concrete placements (then hand-adjustable per §7):

# decor-rules sketch (lives in the .vmap decor section, §11.2)
rule torch_sconce:
  on: walls(material: stone, indoor_or_sheltered)
  place: every 320..448u along walkable frontage, height 96u,
         clearance(front: 64u), not_near(door, 96u)
  prop: props/torch_wall_a   # carries light + fire-effect + soot-source tags (§6, §10)
rule debris_scatter:
  on: floors(concave_corner_dist < 48u)
  place: poisson(r: 24u, density_from: dirt_mask)
  prop: pick[rubble_a, rubble_b, pot_broken] align_to_surface jitter(yaw)
  • Placement families: interval-along-wall (torches, banners, pilasters), poisson-scatter weighted by a mask channel (debris where dirt is, grass tufts where moss is), edge-following (trim/molding along convex edges, cobweb wedges in concave ceiling corners), and point-replacement (upgrade existing map entities — the CURRENT map's candle sconces → CONCEPT's torches).
  • Props are entities, not merged geometry — instanced via MultiMesh where dense, so they replicate, LOD, and delete cleanly. Props carry tags that feed back into §6 (a placed torch becomes a scorch/soot source) — the pipeline loops once: place props → re-run proximity generators.

8.2Decals

Cracks, stain blotches, posters, painted symbols: projected quads clipped to brush faces — DecalSplats' clipping path, minus fade-out, plus serialization. Cheap wins where a mask channel would be overkill (a single distinctive crack vs. a whole "cracked" layer).

8.3Banners & cloth

Detected by texture family + thin-quad shape (or explicitly tagged): replace with a cloth mesh — baked-fold static mesh with a cheap vertex-shader sway (deformVertexes-style, we already implement wave deforms) as v1; actual cloth sim is not needed for the CONCEPT look.

8.4Floor relief

Parallax occlusion mapping on floor-class materials (height already in the layer pack) gives CONCEPT's cobble depth at pixel cost only; true displacement (subdivide + displace at bake) is the fidelity-tier upgrade later. POM first — it needs zero geometry pipeline work.

8.5Terrain & outside-the-map geometry v1.2 · lower priority

Two related jobs: (a) playable terrain patches (ground, hills, courtyard dirt), and (b) vista geometry beyond the playable hull — the mountains behind CONCEPT's walls — where today an imported map just ends at the skybox.

  • Heightfield generation — FBM + ridged noise with domain warping, optional cheap hydraulic-erosion pass for believable gullies; chunked LOD mesh. The layered material system (§5) is terrain splatting — slope/altitude rules drive the layer masks (rock on steep, grass on flat, scree at the transition) through the same generator machinery as §6, so terrain costs almost no new material tech.
  • Vista ring generation — a render-only low-poly ring of mountains/dunes/ruins generated around the map, style-matched to the skybox horizon (shared palette + haze so the mesh fades into the sky, §10.2); parameters: silhouette roughness, distance, height band relative to the map's own skyline. Render-only exactly like amplified geometry (§9) — never collidable, never PVS-relevant.
  • Editing — raise/lower/smooth/flatten height brushes: the same brush-stroke op + tile model as mask painting (§7), writing height texels instead of mask texels. Terrain lives in truth as heightfield + seed params; the bake produces the chunked meshes.
  • Import synergy — the sky-exposure analysis (§4) already tells us where a map opens to sky, i.e. exactly which sightlines vista generation needs to fill.

8.6Foliage — paintable, generatable, reactive v1.2 · lower priority

  • Placement, dual-source like everything else — generators seed per-species density from fields (moss mask → grass tufts and ivy; terrain slope/altitude bands; weeds in concave corners) and a foliage paint brush writes the same density masks by hand — §7's infrastructure verbatim, foliage is just more mask channels. Poisson scatter per species with per-instance style variation: hue shift, scale, bend phase via instance custom data; per-zone species palettes ("dead scrub in the burned wing, lush ivy in the courtyard") through the §6 zone mechanism.
  • Rendering — MultiMesh chunks per species, distance fade to billboards/imposters, no collision.
  • Wind — one global wind state (direction, strength, gust FBM over time) sampled in the foliage vertex shader for sway, with stiffness hierarchy (trunk vs. blade) baked as vertex-color weights. The same wind state feeds weather particles (§10.3) so rain slant and grass lean always agree.
  • Explosions & gameplay reaction — a small ring buffer of recent impulse events (position, radius, strength, timestamp — pushed as per-chunk uniforms) adds a decaying radial bend in the vertex shader: a rocket flattens the grass, it springs back over ~a second; a player wading through bends it at the feet. Optional escalation: destruction — a big explosion clears the density mask locally and hands the spot to the scorch generator (§6), so a rocket fight visibly chews up a meadow.
  • Perf discipline — all reaction is vertex-stage (zero per-instance CPU); chunk updates get a Prof.Sample scope; quality tiers full-react → wind-only → static → off; perf-smoke on the release export before merge (house rules).

8.7Spawn-point presence — auto-detected pads v1.3

Item and player spawn points on classic maps are often bare entities floating over plain floor. Detect, and dress only where needed:

  • Detection — for each item/player spawn entity, probe beneath and around it (short down-trace + small radius query, §4 machinery): is there purpose-built presence — a pedestal/pad brush distinct from the surrounding floor plane, or a decoration prop within radius? Maps that already dress their spawns (pedestals, alcoves, glowing floors) are left alone.
  • Auto-pad where absent — a low ground "bump" pad mesh (a few smoothed-profile variants, material-matched to the floor via the §5 layer system so it reads as built-in rather than pasted on), an optional slow particle ring, and an optional energy cone: a translucent additive cone shader with scrolling energy noise beaming up from pad to item — team-colorable, intensity scaled by item tier (mega > armor > ammo > player spawn). The additive-shader recipes from the bolt/autosprite work apply directly (blend-add with ALPHA=1, the documented LIT-additive traps).
  • Editable like everything else — the pad is a rule-placed prop (§8.1): per-instance override, swap, or delete; style per zone or per map. The point is gameplay legibility: spawns read at a glance on every map, old or new — and it composes with the dynamic item solver (§12.1), which can light cones only under markers that currently hold an item.

9Lattice detection & detail amplification

The spike crowns in the screenshots are the canonical case: brushwork that exists only for silhouette/ornament, built from a few lo-fi brushes because Radiant makes curves painful. The system should find such geometry and regenerate it at higher fidelity — without touching gameplay-relevant collision.

9.1Detection heuristics (scored, then confirmed by a human once per map)

  • Detail content flag — Q3 brushes marked detail (in BSP brush contents) are by definition non-structural. Strongest single signal, already parsed by BspReader.
  • Thinness & silhouette — high surface-area-to-volume, thin in ≥1 axis, high perimeter/area profile; sky behind it (spike crowns literally silhouette against sky faces).
  • Repetition — canonical-form hashing of brush groups (sort planes, quantize, hash) finds repeated instances + their transforms → both a detection signal and the instancing win for free.
  • Non-load-bearing — removing the group doesn't unseal the hull / isn't referenced by gameplay (movers, clips); players never collide with it in typical traces (or it sits above the playable volume).

9.2Amplification strategies (in escalating fidelity)

StrategyWhat it does
v1Bevel + subdivide Chamfer hard edges (2–3 segments), optional curvature-preserving subdivision. Rounded edges catch rim light — a shocking share of CONCEPT's "ornate" read is just this plus warm lighting.
v1Instance consolidation Repeated groups → one amplified mesh, MultiMesh-instanced at all found transforms. Pays for itself in perf even before fidelity.
v2Profile re-extrusion Slice the group perpendicular to its long axis → fit a 2D profile + sweep path → re-extrude with a high-res profile (taper, curve smoothing, ornament presets: finial tips, twists, collars). Turns 6-brush spikes into the CONCEPT's curved horns while preserving the original's proportions and placement.
v2Library substitution Shape-match (dimensions + profile class) against an authored high-detail prop library; scale-fit and swap. Best fidelity ceiling; needs the library to exist. The rule records the match for hand-override (§7).

Invariant: amplified meshes are render-only. Original brushes remain the collision and PVS truth — projectiles, movement, and visibility behave identically on decorated and undecorated versions of a map. (Same discipline as the render-only lean/viewmodel work: presentation never leaks into simulation.)

10Lighting, atmosphere, skyboxes & weather

10.1Lights, GI & post

  • Prop-driven lights — torch/brazier props auto-spawn omni lights with LightStyles flicker and faithful-particle fire + smoke (effects already exist; the prop just references an effectinfo entry). This alone transforms CURRENT's dead sconces.
  • Sun & environment — per-map (per-zone-overridable) directional light + sky settings; tonemap, glow, color grade via the Environment (WorldTint is the existing hook into it). CONCEPT's golden hour is 90% environment settings, 10% everything else.
  • Fog — distance fog for the atmospheric depth on the mountains; optional small volumetric fog volumes near fire for the smoke-haze light shafts. Volumetrics are a quality-tier setting, off by default (perf memory: graphics settings need real wiring, not stubs).
  • Baked GI & the real-time question (v1.3, revised 2026-07-27 with measured findings — the ladder below replaces the earlier one, whose bridge rung turns out not to exist).

    The precondition nobody can skip. The world is drawn by a shader declared render_mode unshaded (game/loaders/LightmapShader.cs): it samples the BSP's precomputed lightmap atlas through UV2 and receives no Godot light at all. Godot lights exist in this project, but only for effects (muzzle flashes, explosions) on model materials. So no GI option below changes a single world pixel until the world has a lit material path. That work is shared by every option and is the first item whichever destination we pick.

    Second precondition, specific to the editor: geometry regenerated from the .vmap document carries no UV2 at all — which is why the editor world currently draws fullbright. Anything baked needs a chart parameterization first.

    Measured API facts (compile-tested against this project's Godot build, not recalled):

    • LightmapGI.Bake(...) does not exist in the C# API. Godot's lightmapper is an editor-only tool driven by the editor plugin; it cannot be invoked from a running game. This kills the previously-planned "LightmapGI batch bake as the bridge" rung for anything in-game.
    • LightmapGI.LightData is settable and RenderingServer.LightmapCreate() exists, so a lightmap baked elsewhere can still be applied at runtime.
    • ArrayMesh.LightmapUnwrap(Transform3D, float) is callable at runtime — Godot's xatlas unwrapper. This is the missing precondition for any in-editor bake: charts can be generated for regenerated geometry without an offline step.
    • VoxelGI.Bake(Node, bool) is callable at runtime.
    • Environment.SdfgiEnabled / SdfgiCascades exist — fully runtime, no bake.

    How Unreal and Unity solve this, since the ask was to line up with them. Both converged on the same two-track answer, and neither uses a baked lightmap for the editing loop:

    • Unreal 5 — Lumen is the default: fully dynamic GI and reflections, no bake, with a software ray-tracing path (screen traces + mesh distance fields) for hardware without RT. Baked lightmaps remain for the low-end tier via GPU Lightmass, which is path-traced, GPU-driven and progressive — you watch it converge in the viewport while you work.
    • Unity — the Progressive Lightmapper (CPU and GPU variants) is path-traced and progressive, prioritizing texels near the scene view so the area you are looking at resolves first. The dynamic side has moved to probe-based GI (Adaptive Probe Volumes); the old realtime-GI solution (Enlighten) is deprecated.

    The shared shape: dynamic GI for the editing loop, progressive path-traced bake for shipped quality, view-prioritized so it converges where you are looking. Our ladder should be that shape — the earlier draft already was; only its bridge rung was wrong.

    OptionProsConsVerdict
    0. Fullbright
    (what the editor does today)    		 Zero cost, zero latency, never wrong while geometry moves. Radiant's own answer. No shape reading — you cannot judge a room's mood or contrast, or whether a corner is too dark. Keep as a render mode, not as the only mode.

    sun + the map's own light entities, real shadows, no GI    		 Instant and always correct — move a brush or a torch and it is simply right. No bake, no charts, no UV2.     2. SDFGI

    3. VoxelGI runtime bake Bakeable from C# in seconds; bounce without a chart atlas; re-bakeable after an edit. Coarse and leaky at Q3 detail scale; bounded volume, so several are needed to cover a map; still a per-frame lookup cost. Cheap fallback where SDFGI is too heavy. Not a destination.

By far the most code: chart packing, a path tracer, tile scheduling, atlas residency. Needs LightmapUnwrap charts for regenerated geometry (available — see above). The destination. Everything else is scaffolding toward it.
    5. Godot LightmapGI batch bake Least code, good quality, already written. Not callable from a running game at all — editor-only (measured). Also wants to own UV2, and cannot ingest the precomputed Q3 pages the parity path uses. Dropped as the bridge. Viable only as an offline step inside the Godot editor.
    6. q3map2 -light Exact parity for untouched classic maps; already how every shipped map is lit. External tool, whole-map only, cannot run incrementally, cannot see props or amplified geometry. Stays for classic BSPs. Not part of the editing loop.

    Recommendation. A ladder, in this order, each rung independently useful:

    1. first · BUILT Light the editor world — give the regenerated world a lit material, spawn the map's light entities as real Godot lights, add the sun and tiered shadows. Precondition for 2–4, and by itself it answers "real-time lighting while editing" and retires the fullbright compromise.
      Built 2026-07-27: EditorLighting spawns the map's light entities as omnis (119 on stormkeep) with a camera-nearest shadow budget, plus a directional sun recovered from the sky shader's q3map_sun; surfaces carrying q3map_surfaceLight are emissive. Both directives are newly parsed — compile-time keys the shipped renderer never needed. cl_editor_lighting 0 returns to fullbright.
    2. preset · BUILT SDFGI behind a quality tier for live bounce, with VoxelGI as the cheaper fallback. This is what UE does for the editing loop.
      Built 2026-07-27: SDFGI on cl_editor_gi, and it does gather from the map's own point lights — measured on stormkeep with the ambient floor at zero, GI adds +2.47 mean brightness with the map's lights and +0.07 with them zeroed, so essentially all the bounce comes from the level's own fixtures. VoxelGI was implemented as the fallback and REMOVED: it rendered black (0.01 mean) and a cvar value that blanks the screen is worse than no fallback. Measurement caution: the first pass concluded SDFGI did nothing, from a crop that was sampling the HUD panel rather than geometry — crop geometry, never the overlay.
    3. destination The progressive GPU lightmapper, converging into the chart atlas while the map sits still, view-prioritized, dirty-tile-scheduled, shipped in the bake cache — the rung that matches GPU Lightmass and Unity's progressive lightmapper, and the only one that produces something a low-end machine renders for free.

    What changed from the previous draft: rung 3 was "LightmapGI batch bake as the stopgap". It is not available in-game, so the stopgap between (1) and (3) becomes SDFGI/VoxelGI — dynamic rather than baked — which is also what both reference engines actually do.

10.2Skybox generation v1.2 · elevated

Skies today are imported six-face cubemaps (classic Q3). Add a parametric sky system as an alternative source, edited live in-game like everything else — its parameters live in the environment section of the .vmap manifest:

  • Layered sky shader — composable layers, each with its own parameters: atmosphere gradient (tint driven by sun elevation), sun/moon discs + halos, 2–3 cloud layers (FBM noise domains scrolling at different speeds, from wispy cirrus to full overcast), starfield (density/twinkle) — and the space style: colored FBM nebulae, planets/moons with correct lit phases, galaxy bands, covering the arena-classic space-map look. Art styles (painted daylight, golden hour, overcast, dusk, deep space, alien) are presets = parameter sets — style variety is data, not code.
  • Bake or live — a static sky bakes to a cubemap at edit time (zero per-frame cost, indistinguishable from an imported sky downstream); a dynamic sky (drifting clouds, weather transitions, day-night if a map wants it) runs the shader live as the Godot sky material. Per-map choice, toggleable in the editor.
  • One sun, one truth — the sky's sun elevation/azimuth/color is the map's directional light and the input to the sun-bleach generator (§6): move the sun in the sky editor and the map re-lights (and on rebake, re-weathers) to match. The classic mismatched-sun-and-skybox artifact becomes unrepresentable.
  • Vista handshake — horizon haze color/height shared with the vista ring (§8.5), so generated mountains sit in the sky rather than pasted in front of it.

10.3Dynamic weather v1.2 · elevated

  • Weather is server-authoritative state — a small state machine (clear → overcast → rain → storm, with transition durations), scheduled or scripted per map, replicated as seed + timeline so every client renders the same sky at the same moment. Editable live: drag the rain slider in the editor and it starts raining for everyone in the session.
  • Precipitation that respects the map — rain/snow as GPU particle volumes spawned only where the sky-exposure field (§4) says sky is visible: no rain indoors, correct drip lines at overhang edges. Splash impacts reuse the client-world particle-collision machinery already built for faithful particles.
  • Weather feeds the material system — rain ramps the wet modifier (§5.2) on sky-exposed texels (darkened albedo, low roughness, puddles growing in AO hollows via the height contest); snow is a white cover layer accumulating on upward-facing exposed surfaces. Both are §6 generators run with a live weather input instead of a baked one — the mask pipeline gains a cheap dynamic term, not a new system.
  • Sound & light — rain loop ducked indoors by the same exposure field; thunder + lightning as LightStyles-style flicker on sun/ambient; wind audio tied to the shared wind state (§8.6).
  • Fairness first — weather defaults to presentation-only: no visibility-relevant fog changes, no movement effects, plus a client reduce/disable toggle and a server enforce-off for competitive modes. An arena shooter can't let weather decide fights unless a mode explicitly opts in.

11.2The .vmap package — editable format = shipping format

One container (directory during development, zip for distribution — same layout, like Godot's pack model), with a strict split between truth (edited, versioned, small) and bake (derived, regenerable, big):

  materials.json    — base-material grammar, layer stacks, per-zone palettes  [truth]
  decor.json        — generator rules + params + seeds, prop rules, amplification decisions [truth]
  paint/            — sparse delta tiles (§7): mask strokes, freezes         [truth]

  bake/             — DERIVED, content-addressed by hash of the truth sections:

    masks/          —   resolved weather-atlas tiles (procedural ⊕ paint)

    light/          —   lightmap atlas / probes (§10)
    vis+collision   —   PVS + collision (from original brushes — unchanged by decoration)
  • The engine loads bake/ — as fast as loading a BSP today (arguably faster: pre-welded, pre-atlased). If bake is missing/stale (hash mismatch), the loader falls back to live generation — slower load, same result, because generators are deterministic (§6).
  • Editing writes only truth sections and dirties bake tiles by hash; a background baker refills them. There is no "decompile" step ever — the brief's ideal ("editable format is the same as the permanent format") holds: you ship the same package you edit, bake cache included.
  • Classic maps stay classic — .vmap is only for decorated/edited maps; the stock BSP path is untouched. A .vmap can reference its source BSP by hash for provenance.

11.3The editor game mode & player states

The editor is a game mode, not a separate application: a server runs mode editor on a map inside the normal NetGame loop — same renderer, same physics, same netcode. That one decision buys instant playtesting (it's the same world), multi-user co-editing (it's already a server), and no editor-only render path to maintain. Each connected player is in one of two states, swapped with a single toggle key:

Gameplay input is repurposed for tools via an editor bind layer pushed over the normal binds (BindTable is already the single chokepoint): attack = tool primary (grab/drag), attack2 = context/alt-constraint, use = cycle tool — all rebindable, live binds shown in the HUD (§11.6).

11.4First-person geometry tools

Design goal: manipulate geometry from inside the world, first-person — no 2D orthographic views in v1. All picking runs against the truth geometry (brushes/patches, §11.2), and every manipulation emits an op (§11.7), which is what makes undo, replication, and saving one mechanism. How you reach these tools, and how you aim a transform at one axis, is §11.9 — this section is the vocabulary, that one is the interaction model. The same tools also operate in the ortho views (§11.5) — they're view-agnostic ops; only the picking and axis constraints differ per view.

  • Pick & selection — camera-ray pick with sub-object resolution: face (plane), edge, or vertex (point), chosen by proximity of the hit to the feature (with a screen-space grab radius so distant vertices are still clickable). Hover highlight before commit; click selects, shift-click multi-selects, whole-brush and whole-entity selection by double-click. Selection references are stable IDs into truth geometry (brush id + face/edge/vert index) so ops replay and replicate deterministically.
  • Move mode — grab handles at the selection center: three axis arrows + three plane pads (world/local orientation toggle); dragging a face body directly slides it along its own plane normal by default (the classic "push the wall out" gesture), modifier for in-plane sliding. While dragging, movement quantizes to the grid (when on) and to geometry snaps (below), whichever binds tighter.
  • Rotate mode — three grabbable rotation rings around the selection center; click a ring, drag to rotate about that axis; angle snapping (5°/15° steps) obeys the same snap toggle; live angle readout at the cursor. Numeric entry (type an angle/distance mid-drag) is a cheap, high-value add.
  • Grid & align built — E2 — a grid fixed in world space that geometry receives: every surface shows the lines where the global grid planes cut through it, so a wall, a slope and a stair display one continuous lattice you can align across the whole map. Power-of-two steps (1u–1024u, Radiant convention), toggleable, fading with distance so it doesn't wallpaper the level; state (on/off · size · keybind) always in the HUD. An align-to-grid action snaps the selection (E3).
    How: deliberately not a projected texture (which would move with the surface and scale with its UVs) and not a screen overlay (which would float in front of the level instead of lying on it). It is one full-screen pass that reads the depth buffer, reconstructs each pixel's world position and lights pixels near a grid plane — so every visible surface is covered automatically, brushes and props and player models alike, with no per-material work and no second copy of the geometry. Line width comes from screen-space derivatives (fwidth) of that reconstructed position, which is what keeps lines ~1px on a distant floor and on a wall seen edge-on rather than aliasing into shimmer.
  • Geometry-to-geometry snapping — while dragging, candidate targets within a threshold pull the drag: vertex→vertex, vertex→edge, edge→edge, and face-plane→face-plane coplanar snap. The active snap is visualized (target highlight + tick). Toggleable with its own keybind (shown in the HUD with the on/off state), threshold a client cvar. Precedence: geometry snap wins inside its radius, else grid.
  • Coordinate readout — the HUD shows the selection center, the live coordinates of the dragged vertex/edge/cursor point during a drag, the delta from drag start, and the dimensions of the selected face/brush. Quake units, Quake coordinate conventions (COORDINATE_CONVENTIONS.md — the same "HUD coords are Quake" rule as the PVS debug work).
  • Entities & props — item spawns, lights, and decoration props (§8) use the same move/rotate handles; point entities get a bounding-box gizmo. This makes the decoration phases' prop-override UX (§7) a free rider on the editor tools.
  • Brush creation E5 — drag-out box creation on a grid plane (most natural in an ortho view, §11.5; in first person: drag a footprint on a surface, then pull height), then reshape with the tools above. Without creation the editor only remixes; with it, you greybox from nothing.
  • Clipper E5 — plane-split of a brush (two/three clicked points, or "cut along current view plane"): the single most-used Radiant power tool, and convexity-safe by construction — both halves of a convex solid are convex, so it sidesteps the trap below entirely. Keep both halves or discard one.
The hard part — convexity Dragging verts/edges/faces on brushes is constraint-solving, not free deformation: brushes must stay convex, so a vertex drag re-derives the containing planes (Radiant vertex-mode semantics) and the op must validate — clamping to the nearest valid position (slide-to-valid) instead of producing degenerate or concave solids, with the constraint telegraphed in the UI (handle turns red, snaps back). This is the highest-unknown piece of the editor and gets prototyped first in E3 (§13), on ugly real-world stock-map brushes.

Derived data while editing: a geometry edit dirties collision, PVS, render meshes, and any baked decoration fields it touches — the same tile-hash dirty model as §11.2's bake cache. Collision refits immediately (PLAYTEST must be honest about the edit you just made); PVS degrades to conservative visibility until an async recompute lands.

11.5Ortho views & render modes

Orthographic top / front / side views — precision editing

A single-pane orthographic view toggled from EDIT (one big view at a time, cycling top → front → side — deliberately not a docked quad layout; this stays an in-game tool, not a desktop app). Orthographic camera, drag to pan, wheel zoom-to-cursor, grid always visible and screen-stable. The view renders truth geometry as wireframe — brush windings drawn as line lists, not the tessellated/decorated render mesh — which is what makes the lines perfectly straight and the drawing exact: selection fills faces translucently, entities draw as boxes with names at sufficient zoom. A scrollable near/far clip slab ("floor filter") moves through the map so stacked floors don't draw over each other — the classic tall-map ortho problem, solved the classic way.

  • Editing in ortho — the same tools, the same ops: pick verts/edges/faces against the projected windings, move with drags that are axis-locked by construction (top view moves XY only; side views XZ/YZ), rotate about the view axis, drag-out box creation, clipper by two clicked points. Because the projection axis is fixed, every manipulation is exactly planar — no accidental depth drift, which is why 2D views remain unbeatable for alignment work.
  • Synced with the world — it's a viewport over the same live world: selection is shared with the 3D view, the fly camera's position + frustum draw in the ortho view, clicking a spot can teleport the fly camera there, and co-editors' edits appear live (they're just ops).
  • Implementation sketch — a second Godot viewport with an orthographic Camera3D over dedicated line-mesh layers (chunked line lists rebuilt only from dirtied brushes), plus a UI overlay for handles/text. The same line set doubles as the 3D wireframe overlay below — one system, two consumers.

What op replication actually turned out to need built

The op channel is built (VmapOpWire, VmapEditServer, NetControl.EditorOp, protocol v20). Four things were not obvious from the sketch above, and each is the difference between co-editing working and two mappers quietly editing different maps.

  • An op that mints an id has to carry it. Create, clip, extrude and paste all allocate ids during apply, and two machines allocating independently diverge the moment either creates anything. The id therefore travels IN the line: a client sends 0 ("you choose"), the server assigns and applies, and the echo is re-encoded from the applied op with the real id. Every peer replays that. One field, and the whole class of id divergence disappears — including on redo, since replaying the same op object reuses the same id.
  • A paste replicates as its result, not as the gesture. "Run my clipboard against your document" needs both sides to hold the same clipboard AND remap ids identically. Sending the objects instead — AddObjectsOp: these solids, these control grids, these spawn keys, these ids — needs neither. Entity ownership travels as INDICES into the op's own arrays, so it means the same thing before and after id assignment.
  • Undo is not an op. It restores a snapshot, so there is no gesture to replay; without something the session diverges the first time anyone presses Ctrl+Z, which in a map editor is within the first minute. What crosses the wire is the state that was put back (SetObjectsOp: these ids now hold this, these ids are gone). Redo and history-travel are the same shape, so one op covers all three.
  • One choke point, not twenty send calls. Replication hangs off VmapEditSession.Applied/Restored rather than off each tool. A tool written next month replicates because it applies an op — not because someone remembered to add a send beside it.

Threading and authority. A submitted op arrives on whichever thread reads packets while the document is owned by the editor on the main thread, so editor_op QUEUES rather than applying; the host drains on the main thread. That is the same second-writer hazard the cross-thread transport race was. A guest does not apply optimistically: it submits and waits for the echo, so an op the server refuses simply never happened rather than being something to roll back. The listen host ignores its own echo arriving back through its loopback client.

Still open: a joining guest imports the map itself rather than receiving the host's document, so a host editing a saved .vmap and a guest importing the BSP would number brushes differently and every replicated op would land on the wrong solid. The guest says so on join rather than diverging in silence, but the document handshake itself — send the truth on connect — is the next piece. Async server bake and tile streaming are also untouched.

11.9Tool selection & usage — the interaction model

§11.4 says what the tools do. This says how you reach them, how you know what you are about to do, and how you aim a transform at one axis instead of three. It supersedes the placeholder key table in §11.6 and the "cycle with a key" scheme E2 shipped.

The problem it fixes is concrete. Today the tool is a cycle on one key, the manipulator is a cycle on another, neither has a menu, the digits are borrowed weapon binds, and a drag grabs the object — so the mouse moves the selection along two screen axes at once and there is no way to say "only Z". None of that is discoverable and the last part is not usable for alignment work.

Handles: two-phase, one axis

The manipulator becomes a target rather than a mode you drag the object under. Click one selects and spawns the handles at the selection centre; click two must land on a handle:

  • Move — three axis arrows + three plane pads (the pads give you controlled two-axis motion when you want it, which is different from getting it by accident).
  • Rotate — three rings, snapped to AngleSnapDegrees (15°, already defined).
  • Scale — six box handles on the selection bounds for per-axis stretch, plus a centre handle for uniform scale. No scale op exists today: ManipulatorMode.Scale is in the enum and drawn in the HUD, and EndDrag handles only rotate and the translate family, so the mode currently does nothing on release. Note the maths — a non-uniform scale transforms brush plane normals by the inverse-transpose, not by the scale itself.

Dragging the object body no longer transforms anything; it selects. That is the whole point: an axis you picked beats an axis inferred from which way the mouse happened to travel. Handles are ray-picked at screen-constant size and win ties against geometry, so a handle in front of a wall is grabbable without flying around it.

Entity authority — the one architectural fork

There are two entity representations and they are not the same object. VmapDocument.Entities is imported from the BSP entity lump and is what gets saved; the items you see floating in an editor session are the server's live entities, spawned by the ordinary game path. The editor world builder renders brushes and patches only, so nothing in the editor currently draws or picks the document's entities at all.

The document is truth, and the two states show different sets. EDIT draws the document's entities; PLAYTEST shows the server's live ones. That falls straight out of what each state is for: EDIT is where you author the map, so it should show what will be saved, and PLAYTEST is a real player in the real world, so it must show what the game actually spawned. It also removes the double-vision the naive version has, where an editor gizmo and a live pickup occupy the same spot and you cannot tell which one your click meant.

Reconciliation therefore happens at the EDIT → PLAYTEST transition, not per-op: entering playtest rebuilds the live entity set from the document. One sync point instead of a sync path threaded through every op, and it is the moment where a rebuild is already expected because the player is being re-placed anyway. Editing stays cheap (ops touch only the document) and playtesting stays honest (what you test is what you just authored).

The alternative — manipulate live entities and scrape them back into the document on save — needs no sync at all but silently drops anything with no live counterpart, and there are plenty: compiler-only classes (_skybox, _decal) never spawn, and the 186 classes in entities.ent do not map one-to-one onto the port's registered spawn functions. Silent data loss on every save is the worse trade.

Point entities need what they have never had here: an EDIT-only render pass (box or modeldisabled model, coloured per entities.ent), a pick path in VmapPicking, and ops for create / move / rotate / delete / set-key. The render pass hides itself in PLAYTEST, which is the same show-mode gating every HUD panel already does.

Waypoints in a free-fly editor

Base's wpeditor spawn and remove require IS_PLAYER, because a waypoint goes at the player's feet with real physics. In EDIT you are a free-flying observer, so the crosshair-on-floor variant (Base's spawn crosshair) is the primary gesture here and the feet-relative ones only make sense after dropping into PLAYTEST. Everything else transcribes directly: jump / crouch / support waypoint kinds, hardwired link origin and destination, link-display lock, the unreachable-waypoint sweep, relink-all, and symmetry origin/axis get-and-set. Links draw as arrows in both the 3D and ortho views, which is the same overlay the entity inspector's targetname→target arrows use (§11.8).

12Gameplay-layer systems v1.3 · lower priority

Systems that generate or consume gameplay rather than visuals. They reuse the doc's core mechanics — determinism by seed, fields as inputs, §7-style override deltas — but operate at the game layer.

12.1Dynamic item placement

The mapper stops hand-picking every ammo box: they place generic markers ("an item could go here", optionally constrained by class hints, size, or mode tags), and a placement solver decides what actually spawns at each marker — if anything — from balance parameters:

  • Inputs — the marker set; the nav graph (bot waypoints — travel time between markers, not euclidean distance); room/zone structure (§4); gamemode + expected player count (§12.2 metadata); a balance parameter set (weapon coverage per map-minute, ammo-to-weapon pairing radius, major-item spacing floors, contested-vs-safe placement bias); optionally heatmap data (§12.3) as a demand signal.
  • Solver sketch — majors first (mega/armor placed to maximize pairwise nav-distance subject to spacing floors — the classic control triangle emerges naturally), then weapons for coverage (every zone within T seconds of a weapon), then ammo paired to the weapons that consume it, then health filler. Greedy with local-swap refinement is enough — it's dozens of markers, not thousands.
  • Deterministic by construction — seeded by (map hash, balance-params hash, mode, player-count bucket): same settings on the same map ⇒ the identical layout on every server, every restart. Different modes get different solutions, stored per mode in the .vmap. Retune one balance parameter and every map's layout follows — the whole rotation rebalances from one knob.
  • Manual override, as always — pin an item to a marker, ban a class from a marker, or hand-place outright; overrides are §7-style deltas the solver must respect. Importing a classic map turns its existing item entities into pinned placements — nothing changes until you ask. Pads/cones (§8.7) light only under markers that currently hold an item.

12.2Player-count-aware map selection

  • Metadata lives in the map — the .vmap manifest (a sidecar for classic BSPs) carries per-mode suggested player ranges (min / sweet spot / max) plus a size class. Seeded automatically from measurable proxies — playable area, route lengths, spawn and item counts — then mapper-overridable, and refinable from §12.3 telemetry (a map that empties the server at 12 players tells on itself).
  • Selection honors it — the vote screen sorts and badges candidates by fit to the current player count, with a cvar to restrict to fitting maps outright; auto-rotation draws from the fitting set with recency damping. Playlists may declare per-entry bounds overriding the map's own.

12.3Demo-driven heatmaps

Demos (the streaming .xgd format) already record what's needed: positions every snapshot, shots, damage events. Mine them:

  • Extraction — an offline pass over one demo accumulates per-map grids: player presence (time-weighted position density), shots fired (origins + directions), damage dealt (impact position, amount, weapon).
  • Aggregation — grids sum trivially across demos: per map, per mode, per server, per date range — a server can fold in every demo it has ever recorded. Stored as tile files keyed by map hash, so geometry edits don't silently mix incompatible data.
  • Display — editor debug channels (§11.5): presence / shots / damage overlays painted onto the world in chart space, with a time-range scrubber.
  • Four customers, one data source — mappers (dead zones, chokepoints, unused routes); the item solver (§12.1 demand signal); the traffic-wear generator (§6 — real player traffic replacing the bot-nav estimate); metadata refinement (§12.2).

14Risks & open questions

  • Perf ceiling — 4 extra material layers with triplanar + height blending is real fragment cost on a game that fights for frames (steady-state FPS work says render-submission CPU is the current gap; this adds GPU). Mitigations: quality tiers from day one, single-sample triplanar, mask-driven early-out (most texels have ≤1 active layer), measure on the release export per house rules. Open: budget — how many ms is decoration allowed to cost at "high"?
  • Texture art dependency — layer packs (moss/dirt/soot/wear/wet with height) must come from somewhere. CC0 PBR libraries (ambientCG et al.) cover v1; a curated, license-clean set needs choosing and shipping (asset-repo question, cf. the voice-audit precedent for asset governance). Open: who curates, target resolution/memory (Texture2DArray forces uniform size)?
  • Two material worlds — Q3-stage parity materials vs. layered decorated materials must coexist per-surface (a decorated map still has parity shaders on liquids, autosprites, skies). The generated-shader system needs a clean "base provider" seam so a layered material can wrap either a Q3 stage result or a PBR base without combinatorial explosion. Open: do decorated maps eventually want a PBR base path for stock textures (normal-map generation from diffuse?), or stay Q3-base + layers indefinitely?
  • UV2 double-booking — masks and lightmaps both want chart space. Same charts at different densities is the plan (§5.1/§10). Answered 2026-07-27: the question is moot for the in-game path — LightmapGI.Bake does not exist in the C# API at all (compile-tested), so LightmapGI never gets to own UV2 in a running game. Runtime chart generation via ArrayMesh.LightmapUnwrap is available, so our own charts stay the single parameterization for both masks and lightmaps. Open: chart density — one atlas at mask density with lightmaps sampled at a coarser mip, or two atlases sharing a layout?
  • Bake-cache size & distribution — weather atlas + lightmaps + amplified meshes could be tens of MB per map; fine on disk, needs care on the wire (content download path, delta by tile hash). Open: compressed tile format (BC7 at rest?) and the download-resume story.
  • Editor scope creep — "in-game editor" is a product-sized phrase. The line that keeps v1 shippable: first-person tools + single-pane ortho views + clipper — no docked quad-view desktop UI, no boolean CSG ops (subtract/hollow), no bezier-patch authoring until the E-track loop is proven in real mapping sessions. Open: concrete default keybinds for state toggle / tools / grid / snap / view modes (HUD reads live binds either way, §11.6).
  • Convex-brush editing UX — vertex/edge drags on convex solids are constraint-solving (§11.4): a drag can demand a non-convex result or collapse faces to slivers, and the plane-refit op must clamp to valid rather than corrupt geometry. Front-loaded into E3 deliberately; prototype on ugly stock-map brushes, not clean test cubes. Open: allow per-object escape to general (non-brush) mesh geometry in truth, or stay brushes-only?
  • Derived-data invalidation while editing — one geometry drag dirties collision, PVS, render meshes, and overlapping baked fields. Collision must refit immediately (PLAYTEST honesty); PVS may degrade to conservative visibility until an async recompute lands. The dirty-tracking granularity (brush → tile) is shared infrastructure with the decoration bake — design it once, in E0.
  • Live-world systems cost & sync (v1.2) — weather, wind, and reactive foliage are this doc's first continuously animated decoration (everything else is bake-static). Each is a per-frame system (Prof.Sample + perf-smoke per house rules) with a hard off-switch and quality tiers, weather is presentation-only by default (§10.3 fairness rule), and weather/wind state is new replicated state. Open: does weather ride the settemp/cvar replication path or the entity path?
  • Determinism drift — client-side regen (§11.7) requires bit-stable generators across platforms (float traces!). Mitigation: fixed-point field quantization before mask math, or simply keep server-bakes-everything until proven painful. Open: is client regen ever actually needed beyond paint preview?
